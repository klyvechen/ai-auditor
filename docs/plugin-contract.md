# Plugin Contract

這份文件定義「一個模組要怎麼被掛進 AI-Auditor 框架」。內容整理自 email-assist repo 交接的介面約定([`email-assist/app/README.md`](../../email-assist/app/README.md) 的「位置與原則」一節、[`shell.dart`](../../email-assist/app/lib/ui/shell.dart) 的實作),目前以 email-assist 為唯一參考範例。

## 1. 模組只透過自己的 `Shell` widget 對外

- 每個模組是獨立 repo/套件,對框架只暴露一個頂層 widget(慣例命名 `Shell`)。
- `Shell` 內部自己管理「這個模組自己的頁面」怎麼切換(例如 email-assist 用一個頂部 `TabBar` 管 5 個頁面),**不管視窗寬窄都是同一套**,不會自己做左側選單或底部導覽。
- 框架把 `Shell` 直接嵌進內容區,不需要理解、也不應該去改動 `Shell` 內部的頁面結構。
- **`Shell` 必須自給自足**:自己完成初始化(讀本機設定、建立自己的 state 管理等),框架不需要、也不應該知道模組內部用了什麼狀態方案才能讓 `Shell` 動起來。框架端除了 `import` 跟把 widget 放進樹裡,不應該再寫任何模組專屬的初始化程式碼(驗收範例見「嵌入方式」)。email-assist 的參考實作:`Shell` 是外層的自我初始化 widget(讀 `SharedPreferences` → 建 `AppState`/`BulkState` → `MultiProvider` → 渲染實際內容),實際頁面內容搬進另一個 public class(`ShellContent`)——那個 class 只是為了讓模組自己的 widget 測試能直接塞假資料進去,不是給框架用的,框架只認 `Shell`。**模組可以有框架用不到的其他 public export,這不違反「唯一入口」原則**,只要框架端真的只需要 import `Shell` 就能動就好。
- **建議每個模組自帶一個驗證自給自足的測試**:在乾淨的 `MaterialApp` 裡直接塞 `const Shell()`,不做任何額外設定,確認不會因為缺 provider/依賴而炸掉。這個測試就是把「嵌入方式」那段的最小範例直接寫成程式碼跑,能防止以後不小心破壞這條契約。email-assist 已經有這個測試(`app/test/shell_test.dart`),可以當範本。

> **釐清**:這條限制的是「模組要不要自己做跨頁面的頂層導覽」(左側選單、底部導覽列、依視窗寬窄切換整體導覽樣式)。模組**單一頁面內部**要怎麼因應寬度排版(例如單欄/雙欄、要不要用底部面板顯示詳情)完全是模組自己的自由,跟這條規範無關,不算違規。

## 2. 跨模組導覽是框架的責任

- 框架要有一個「模組選單」(例如左側垂直選單),列出目前掛載的模組,點一個就把對應模組的 `Shell` 換進內容區。
- 目前只有 email-assist 一個模組,但選單架構要留可以擴充(見 [`modules.json`](../modules.json))。

## 3. 手機版整體殼是框架的責任

- 模組自己的內容(例如 email-assist 的水平 Tab)在手機上維持原樣,模組不會、也不需要為手機另外做版面。
- 「怎麼在小螢幕上呈現選模組這件事」由框架另外設計,不是把左側選單直接塞進手機版了事。
- 尚未決定實際呈現方式,見下方開放問題。

## 4. 每個模組優先用自己的金鑰,沒有的話可以跟框架要

- 模組的前端**不保存**真正的服務金鑰(Gmail token、AI API key 等),只保存「自己後端的網址 + API_TOKEN」這類連線資訊。這條不變。
- 每個模組**優先自備**真正的服務金鑰,存在模組自己的後端(不在前端,也不在框架層)。email-assist 目前就是這樣:Gmail/MiniMax 金鑰只在 `backend/.env`。
- 如果一個模組**沒有自己的金鑰**(例如還沒申請、或就是想沿用框架已經備妥的共用金鑰),可以向框架要。框架可以持有一份「共用金鑰」,發放給有需要的模組後端使用。**這是模組自願選擇的補位方案,不是預設路徑**——有自己金鑰的模組完全不需要跟框架有任何金鑰往來,框架也不會主動要求模組交出或改用框架的金鑰。
- 框架本身不理解、不驗證模組自己金鑰的有效性,那始終是模組自己後端的責任。框架只對「自己發放出去的共用金鑰」負責。
- **機制細節尚未定義**,見下方「尚未決定的問題」第 4 點:框架怎麼保管共用金鑰、模組後端怎麼證明自己有資格拿、拿到之後的用量與外洩風險算誰的。

## 5. 模組 = 後端 + 前端兩塊,各自獨立

- 模組通常會有平行的 `backend/` + `app/`(或類似命名)兩個資料夾,兩者只靠 HTTP + Bearer token 溝通,框架不需要理解這層。
- 框架只需要:
  - 知道怎麼啟動/連到這個模組的前端 UI(嵌入 widget,或未來若技術棧不同則開子視窗/webview)。
  - **不需要**管模組的後端要怎麼跑——那是模組自己的 repo 負責(例如各自 README 寫怎麼 `uv run <module> serve`)。框架文件最多提醒使用者「先照模組自己的 README 把後端跑起來」。

## 嵌入方式

- **同技術棧(Flutter → Flutter)**:模組的 `Shell` 當作套件,用 path dependency 直接 `import` 進框架,同進程渲染,沒有額外整合成本。這是目前(email-assist)採用的路徑。
- **不同技術棧**:框架端改用獨立視窗或 webview 嵌入模組的 UI,模組本身仍照上面 1~5 點的原則設計自己的 `Shell`(或等價的「自己對外的唯一入口」),但框架這邊的嵌入程式碼要另外處理跨進程/跨技術棧的整合(例如 postMessage、獨立視窗生命週期)。AI-Auditor 目前選擇 Flutter 作為框架本體,優先支援第一種路徑。

**「沒有額外整合成本」的驗收基準**:框架端除了在 `pubspec.yaml` 加 path dependency,程式碼大概就只需要這樣,不應該再多寫模組專屬的初始化:

```dart
import 'package:email_assist/ui/shell.dart';

// 模組選單點到 email-assist 時,直接把 Shell 放進內容區:
Widget content = const Shell();
```

如果框架端需要額外知道模組內部用了什麼 state 方案、要自己建 Provider/DI 才能讓 `Shell` 動起來,就代表不合格,要回頭改模組那邊(見第 1 點的自給自足要求)。

## 一個模組要符合的最低要求(checklist)

- [ ] 暴露一個頂層 widget/元件作為對外唯一入口(對 Flutter 模組建議命名 `Shell`)。
- [ ] 這個入口自己處理模組內部的頁面切換,不管視窗寬窄用同一套版面。
- [ ] 不在前端保存真正的服務金鑰,只存「自己後端的連線資訊」。
- [ ] 前端與後端是兩個獨立專案,只靠 HTTP(+ token)溝通;框架不需要讀懂後端邏輯。
- [ ] 在 [`modules.json`](../modules.json) 登記一筆(id、顯示名稱、怎麼找到這個模組)。

## 已拍板的決定

- **模組怎麼註冊**:目前由 AI-Auditor **手動維護** [`modules.json`](../modules.json)。等有第二個模組要掛進來,再評估要不要改成模組自帶 manifest 讓框架自動掃描/發現。
- **Shell 自給自足怎麼做**:初始化包裝邏輯包進 `Shell` 本身(不是另開一個 `EmailAssistModule` 類別),`import` 路徑與 `entrypoint: "Shell"` 都不用改。email-assist 已經照這個方向改完並補上驗證測試,見上面第 1 點。

## 尚未決定的問題

1. **連線設定怎麼存**:目前每個模組的「後端網址 + token」存在模組自己的本機儲存(email-assist 用 Flutter `shared_preferences` / web 版用 localStorage)。框架介入後要不要統一集中管理(例如框架存一份、轉發給各模組),還是繼續讓各模組各管各的?傾向繼續各管各的,理由見第 4 點,但尚未拍板。
2. **手機殼長怎樣**:選項之一是「選模組 → 進去後模組內容佔滿全螢幕(加一顆返回選單的按鈕)」;也可能有別的呈現方式(例如底部模組切換列)。尚未決定。
3. **未來模組如果不用 Flutter**:框架已經選定 Flutter 本體,若之後有模組想用別的技術棧,要用「嵌入方式」一節提到的獨立視窗/webview 路徑,實際整合方式(要不要統一走 webview、怎麼處理視窗生命週期)還沒設計。
4. **共用金鑰怎麼發放**(新增,見第 4 點):框架要不要自己有一個小後端來保管/驗證/發放共用金鑰?模組後端要透過什麼方式跟框架要(HTTP API?本機設定檔?)、怎麼證明自己有資格拿?拿到之後這把金鑰的用量與外洩風險算誰的?這幾件事目前只確立了「模組沒有自己金鑰時可以跟框架要」這個原則,實際機制還沒設計。真的要設計時,email-assist 提醒了三個要先想清楚的風險:
   - **追責**:provider(Gmail/AI 服務商等)看到的用量、限流、停用都是「框架」這個身份,分不出是哪個模組造成的——框架需要自己做一層 per-模組的用量記錄/標記,不然某模組把配額用爆,框架不知道該斷誰。
   - **炸半邊**:如果所有補位模組真的共用同一把 key,一個模組濫用導致這把 key 被 provider 停權,會連坐所有用這把 key 的模組,風險等級跟「各自獨立金鑰」完全不同。如果 provider 支援一個帳號開多把 key,應該考慮「每個補位模組各發一把獨立 key(都算在框架帳下)」,把炸掉的範圍限制在單一模組,而不是真的所有人共用同一把。
   - **認證機制本身就是新的祕密**:模組後端要怎麼向框架證明身份、換到共用金鑰,這個認證憑證本身也需要考慮輪替、撤銷、外洩處理——它是框架層新增的攻擊面,不因為是「補位方案」就比較不重要。
